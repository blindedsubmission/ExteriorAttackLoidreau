# AI disclosure and implementation provenance

We view the exact implementation details as non-material. Our primary
concerns were performance and portability to ensure easy reproduction.
Our work presents an attack on an encryption scheme and is not
concerned about whether or not the code runs in constant time or
resists side channel analysis.

The implementation was practically entirely generated by use of the
open weight LLMs GLM-5.3 and GLM-5.3-Flash in ZCode Desktop version
3.12.3. The development history can be summarized as follows:

1. A simple python prototype from an earlier draft of the paper, this
   was used to test whether the distinguisher works.
2. To test larger parameter sets, we then prompted for an
   implementation in C++ together with a bitsliced glsl shader for
   higher performance in the kernel search phase.
3. We used GPT 5.6 Sol to find further optimizations of the
   computationally expensive kernel search phase. This includes not
   materializing the stacked compound matrices by using (block)
   Wiedemann.
4. For improved stability, portability and to ensure memory safety, we
   decided to prompt for a reimplementation of the kernel search with
   all obtained improvements in rust targeting both CPU and optionally
   GPUs via wgpu.

We intentionally decided to keep key generation, key recovery from the
recovered kernel and subsequent decryption with the obtained functional
private key in python for easier readability. To allow the code to be
scrutinized more easily, we asked the LLM to generate additional
supporting documentation outlining relevant design choices
(ARCHITECTURE.md) and a specification for the key format
(SPECIFICATION.md). Finally, we also made sure the variable names align
with those in the paper as much as possible.

## Correctness

The attack is randomized. It never returns a wrong key, but a solver
seed can fail to find a kernel, in which case one simply reruns with
another seed. Correctness of a result is therefore not established by
trusting the (LLM generated) code. Instead, the code checks every
result itself:

- the solver only accepts a kernel candidate if it is a nonzero null
  vector of the raw unconditioned public stack (W p == 0)
- recovery re-derives an equivalent key from public data alone and
  re-verifies every step (plane rank conditions, shift system, twisted
  norm and Hilbert 90, rowspace identity)
- the demo decrypts fresh ciphertexts made with the public key using
  the recovered key alone
- pipeline.py verify runs a negative and a tamper control so the checks
  cannot pass vacuously
- bring_your_own_key.py feeds the pipeline a key from an independent
  implementation and checks the recovered key against the specification

A run that ends in PASS has thus recovered a functional private key
from a public key. The parameter constraints needed for this
(SPECIFICATION.md, Section 4) are met by nearly all published parameter
sets.

The implementation is deterministic by design (seeded randomness, order
free arithmetic over GF(2^m), no floating point). We do not merely rely
on the LLM's claim that this holds. The CPU and GPU paths give exactly
the same output for the same seed, and runs on different machines agree
as well. We additionally provide traces and SHA256 checksums for
comparison in traces/, the exact inputs are listed in
traces/README.md and the validation runs in VALIDATION.md.

During development, we extensively tested the implementation and
development versions across a wide range of different compute
platforms: a thinkpad laptop (intel i5), an old server CPU, an old
consumer GPU (GTX 1080 Ti), a new server CPU, and two consumer GPUs
(RTX 4090, RX 6800 XT).
